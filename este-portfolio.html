📋 Visão Geral do Projeto

Este site nasceu de uma necessidade simples, mas cresceu para se tornar um dos projetos mais desafiadores e gratificantes que já desenvolvi. A ideia inicial era ter um espaço profissional para apresentar meus projetos e experiências na área de equipamentos biomédicos. Porém, no processo, percebi que construir um site do zero era, por si só, um projeto que merecia ser documentado — e é exatamente isso que esta página faz.

O que começou como um site estático em HTML/CSS/JS puro evoluiu para uma aplicação completa com Jekyll, modo escuro, animações, lightbox, sistema de "ver mais", e uma infinidade de detalhes que foram ajustados ao longo de semanas. Cada seção desta página é um reflexo de uma decisão técnica, um problema superado ou uma lição aprendida.

Abaixo, você encontrará uma documentação detalhada de todo o processo — do planejamento à implementação final — incluindo as dificuldades que enfrentei, o que aprendi em cada etapa e por que tomei determinadas decisões. Este é, literalmente, um diário de bordo.

🗓️ Histórico de Desenvolvimento

Antes de entrar nos detalhes de cada fase, quero contextualizar o momento em que esse projeto começou. Estava no meio do curso técnico de Equipamentos Biomédicos, com projetos acadêmicos se acumulando (Eye Tracker CK², Monitor Multiparamétrico, Guia de Respiração) e percebi que precisava de um lugar para organizar tudo isso. Foi aí que decidi construir meu próprio site.

O desenvolvimento não foi linear. Passei por várias fases, algumas com avanços rápidos e outras com semanas de travamento. Ao longo do caminho, tive que aprender novas tecnologias, revisar decisões anteriores e, às vezes, refazer coisas que já estavam prontas. Tudo isso faz parte do processo, e é exatamente isso que quero documentar aqui.

Concepção e Planejamento

Definição do objetivo do site, levantamento de conteúdo (projetos, publicações, conquistas) e criação do primeiro wireframe. A decisão mais importante foi não usar frameworks — tudo seria feito com HTML, CSS e JavaScript puro.

Primeira versão: HTML/CSS/JS

Construção das primeiras páginas (Home, Sobre, Projetos) com CSS grid, flexbox e JavaScript para o menu mobile. Primeiras animações de fade-in implementadas.

Migração para Jekyll

O site cresceu e a repetição de HTML se tornou um problema. Migrei para Jekyll, que permitiu separar navbar, footer e layouts. Hospedagem no GitHub Pages.

Modo Escuro e Personalização

Implementação do dark mode com detecção de preferência do sistema e persistência via localStorage. Ajuste de todas as cores, sombras e bordas para os dois temas.

Animações e Microinterações

Implementação de fade-in com Intersection Observer, efeito stagger nos cards, tilt 3D nos cards de projeto e parallax suave no hero.

Lightbox e Galeria

Criação de um sistema de lightbox genérico para ampliar imagens em projetos e publicações, com navegação por teclado (setas, Escape) e suporte a gestos.

SEO e Acessibilidade

Adição de JSON-LD, Open Graph, robots.txt, sitemap.xml, skip-links, ARIA labels e correção de problemas de contraste. Testes com Lighthouse.

Refinamentos Finais

Otimização de imagens (WebP), correção de bugs de responsividade, página 404 personalizada e ajustes finos de tipografia e espaçamento.

🔨 Fase 1: O Início — HTML e CSS Puro

Quando decidi criar o site, a primeira decisão foi não usar nenhum framework (React, Vue, etc.) nem construtores de sites (Wix, WordPress). Queria entender cada linha de código e ter controle total sobre o resultado. Além disso, como estudante de equipamentos biomédicos, não tinha formação específica em desenvolvimento web, então tudo seria aprendido na prática.

O Wireframe

Comecei desenhando à mão a estrutura das páginas. O site precisava ter:

  • Home — apresentação pessoal, links para redes sociais e botão de download do currículo;
  • Sobre — história, formação e áreas de interesse;
  • Projetos — galeria com os projetos técnicos e acadêmicos;
  • Publicações — artigos, registros de aulas práticas e participações em eventos;
  • Conquistas — medalhas, certificados e reconhecimentos;
  • Contato — canais de comunicação.

A princípio, queria fazer tudo em uma única página (one-page site), mas percebi que o conteúdo era muito extenso. Então, optei por múltiplas páginas, o que exigiria mais trabalho, mas resultaria em uma experiência mais organizada.

Desafios na Fase 1

Grid e Flexbox foram os primeiros obstáculos. Eu não tinha experiência com esses conceitos, então assisti a vários tutoriais e estudei a documentação do MDN. Na época, ainda não entendia bem como fazer layouts responsivos, então o site era basicamente focado em desktop.

Outro problema foi o menu mobile. Eu queria um menu hambúrguer que funcionasse bem, mas meu primeiro código era simplesmente um botão que mostrava/escondia o menu. Faltava suporte a teclado, fechamento por clique fora e animações suaves.

Aprender na prática foi a melhor parte. Cada erro me ensinava algo novo. Por exemplo, descobri que usar display: none para esconder o menu mobile impedia que animações de transição funcionassem. A solução foi usar position: fixed com right: -100% e transição em right.

⚙️ Fase 2: Migração para Jekyll

Depois de construir as primeiras páginas, percebi que estava repetindo muito código. O navbar, o footer e o head (meta tags, links de fontes, CSS) se repetiam em todos os HTML. Se eu quisesse mudar uma única coisa no navbar, teria que editar todas as páginas. Isso era insustentável.

Foi quando descobri o Jekyll, um gerador de sites estáticos escrito em Ruby. A ideia era simples: você escreve templates (layouts) e arquivos parciais (includes), e o Jekyll gera as páginas HTML finais.

Estrutura do Jekyll

Criei uma estrutura assim: 

/
├── _includes/
│   ├── navbar.html     # Menu de navegação
│   └── footer.html     # Rodapé
├── _layouts/
│   └── default.html    # Layout base com head, header e footer
├── _data/
│   └── conquistas.yml  # Dados das conquistas (medalhas)
├── images/             # Ativos visuais
├── *.html              # Páginas (index, sobre, projetos, etc.)
├── _config.yml         # Configuração do Jekyll
└── style.css           # CSS global

A migração não foi difícil porque eu já tinha o HTML pronto. Basicamente, movi o código do navbar para um arquivo separado, o mesmo para o footer, e criei um layout base.

Dificuldade: Links com baseurl

Um dos problemas que enfrentei foi o baseurl. Como o site estava hospedado em https://kelvinsaldanha.github.io/portfolio/, todos os links precisavam incluir o caminho /portfolio. No começo, eu colocava os links manualmente, o que era chato e propenso a erros.

A solução foi usar o filtro relative_url do Jekyll: 

{% link /sobre/ | relative_url %}

Isso gera automaticamente o caminho correto com o baseurl. Foi um aprendizado importante — entender como o Jekyll lida com URLs relativas e absolutas.

Dificuldade: Configuração do YAML Front Matter

No início, eu não entendia bem como o front matter (bloco de metadados no topo dos arquivos) funcionava. Colocava layout: default em todas as páginas, mas esquecia de adicionar title, description e permalink. Isso fazia com que o título do site ficasse sempre o mesmo em todas as páginas, prejudicando o SEO.

Depois de algumas pesquisas, implementei defaults no _config.yml: 

defaults:
  - scope:
      path: ""
    values:
      layout: "default"
      author: "Kelvin Saldanha"
      lang: "pt-BR"

Isso garantiu que todas as páginas tivessem o layout correto sem que eu precisasse repetir o front matter.

🌙 Fase 3: Modo Escuro e Personalização

Uma das funcionalidades que mais orgulho me dá é o modo escuro. Não é apenas uma troca de cores — é um sistema completo que respeita a preferência do usuário e permite alternância manual.

Como funciona

O CSS utiliza variáveis nativas (CSS Custom Properties) definidas em :root: 

:root {
    --color-background: #0a0e1a;
    --color-surface: #111827;
    --color-text: #f1f5f9;
    --color-text-muted: #94a3b8;
    --color-primary: #3b82f6;
    /* ... */
}

[data-theme="light"] {
    --color-background: #ffffff;
    --color-surface: #f8fafc;
    --color-text: #0f172a;
    --color-text-muted: #475569;
    /* ... */
}

O JavaScript detecta a preferência do sistema com window.matchMedia('(prefers-color-scheme: dark)') e armazena a escolha do usuário no localStorage: 

function getTheme() {
    const saved = localStorage.getItem('theme');
    if (saved) return saved;
    return prefersDark.matches ? 'dark' : 'light';
}

function applyTheme(theme) {
    document.documentElement.setAttribute('data-theme', theme);
    localStorage.setItem('theme', theme);
    updateDarkModeIcon(theme);
}

Dificuldades

O maior desafio foi garantir que todos os elementos tivessem cores adequadas para ambos os temas. Era comum esquecer de definir uma variável para um elemento específico, o que resultava em contraste ruim no modo claro ou escuro.

Por exemplo, os cards usam var(--color-surface) como fundo. No tema escuro, isso é #111827 (quase preto), e no tema claro, #f8fafc (quase branco). Se eu usasse #fff fixo em algum lugar, não funcionaria bem no modo escuro.

Outra dificuldade foi o flicker (piscar) ao carregar a página. Como o JS roda após o HTML, o site carregava no tema claro e depois mudava para o escuro, causando um flash. A solução foi adicionar um script inline no <head> para aplicar o tema antes do primeiro render: 

<script>
    (function() {
        const saved = localStorage.getItem('theme');
        const prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
        const theme = saved || (prefersDark ? 'dark' : 'light');
        document.documentElement.setAttribute('data-theme', theme);
    })();
</script>

Isso eliminou o flicker completamente. Aprendi que, para temas dinâmicos, o JavaScript deve rodar o mais cedo possível.

✨ Fase 4: Animações e Microinterações

Depois de ter o site funcional, queria que ele fosse vivo. As animações não são apenas estéticas — elas guiam o usuário, transmitem personalidade e melhoram a experiência de navegação.

Fade-in com Intersection Observer

O primeiro passo foi implementar animações de entrada nos elementos ao rolar a página. Usei o IntersectionObserver, uma API nativa que detecta quando um elemento entra na viewport: 

const observer = new IntersectionObserver((entries) => {
    entries.forEach(entry => {
        if (entry.isIntersecting) {
            entry.target.classList.add('visible');
            observer.unobserve(entry.target);
        }
    });
}, {
    threshold: 0.1,
    rootMargin: '0px 0px -50px 0px'
});

animatedElements.forEach(el => observer.observe(el));

A classe fade-in define opacity: 0 e transform: translateY(20px), e a classe visible redefine para opacity: 1 e translateY(0). A transição é feita com CSS.

Efeito Stagger (Cascata)

Para dar um efeito de cascata, adicionei um atraso progressivo com base no índice do elemento: 

allFadeElements.forEach((el, index) => {
    const isStagger = staggerSelectors.some(selector => el.matches(selector));
    if (isStagger) {
        el.style.transitionDelay = (index * 0.05) + 's';
    }
});

Isso faz com que os cards entrem um após o outro, criando um fluxo visual agradável.

Tilt 3D nos Cards de Projeto

Uma das microinterações mais legais foi o efeito tilt 3D nos cards de projeto. Quando o mouse passa sobre um card, ele se inclina levemente, como se estivesse "olhando" para o cursor: 

card.addEventListener('mousemove', (e) => {
    const rect = card.getBoundingClientRect();
    const x = e.clientX - rect.left;
    const y = e.clientY - rect.top;
    const rotateX = ((y - centerY) / 40) * -1;
    const rotateY = (x - centerX) / 40;
    card.style.transform = `perspective(1000px) rotateX(${rotateX}deg) rotateY(${rotateY}deg)`;
});

O divisor 40 controla a intensidade — quanto maior, mais suave. Ajustei esse valor várias vezes até encontrar um equilíbrio entre sutil e perceptível.

Dificuldades

Uma das dificuldades foi garantir que as animações não interferissem no desempenho. O IntersectionObserver é eficiente, mas o tilt 3D usa transformações frequentes. Descobri que will-change: transform ajuda a GPU a otimizar, mas não devo usar em muitos elementos ao mesmo tempo.

Outro desafio foi a redução de movimento. Usuários com prefers-reduced-motion devem ter as animações desativadas. Implementei: 

@media (prefers-reduced-motion: reduce) {
    *, *::before, *::after {
        animation-duration: 0.01ms !important;
        transition-duration: 0.01ms !important;
        scroll-behavior: auto !important;
    }
}

Isso foi um aprendizado importante sobre acessibilidade — nem todos os usuários conseguem (ou querem) ver animações.

🖼️ Fase 5: Lightbox e Galeria de Imagens

O lightbox é um recurso que permite ampliar imagens em um modal, com navegação entre elas, fechamento por teclado (Escape), setas para avançar/voltar e uma legenda. Implementei um sistema genérico que funciona em qualquer página.

Como funciona

O JavaScript seleciona todas as imagens com classes específicas (.post-card__image e .figura-card img). Ao clicar, abre o modal com a imagem ampliada. A legenda é extraída do título do post ou da legenda da figura: 

function abrirLightbox(index) {
    indiceAtual = index;
    const img = itens[indiceAtual];
    imagem.src = img.src;
    imagem.alt = img.alt || '';
    
    // Tenta extrair legenda
    const postCard = img.closest('.post-card');
    if (postCard) {
        const titulo = postCard.querySelector('.post-card__title');
        if (titulo) legenda.textContent = titulo.textContent.trim();
    }
    
    contador.textContent = `${indiceAtual + 1} / ${itens.length}`;
    lightbox.classList.add('lightbox--ativo');
    document.body.style.overflow = 'hidden';
}

Dificuldades

O maior desafio foi lidar com a legenda dinâmica. Cada imagem precisa de uma legenda diferente, e algumas não têm. Tive que criar uma lógica flexível que busca a legenda no DOM, mas também permite um fallback.

Outra dificuldade foi o evento de clique — algumas imagens são clicáveis, outras não. Se uma imagem não tem um src válido (por exemplo, quando o arquivo não existe), ela não deveria abrir o lightbox. Filtrei os itens com: 

const itens = Array.from(imagens).filter(img => img.src && !img.src.includes('undefined'));

Isso evita que o lightbox abra uma imagem quebrada.

Também descobri que o scroll-behavior: smooth no CSS pode atrapalhar o lightbox quando o modal é aberto. A solução foi adicionar overflow: hidden no body enquanto o lightbox estiver aberto, e remover ao fechar.

🔍 Fase 6: SEO e Acessibilidade

Depois que o site estava funcional e bonito, percebi que ele precisava ser encontrado por mecanismos de busca e acessível para todos os usuários, incluindo aqueles que usam leitores de tela.

SEO (Search Engine Optimization)

Implementei várias práticas de SEO:

  • Meta descrições — únicas para cada página;
  • Open Graph e Twitter Cards — para compartilhamento em redes sociais;
  • JSON-LD — dados estruturados para o Google entender o conteúdo;
  • sitemap.xml — lista todas as páginas;
  • robots.txt — instruções para rastreadores;
  • URLs semânticas — uso de permalink legível.

O JSON-LD foi o mais complexo. Criei um script no layout base que descreve a pessoa (com @type: Person) e as conquistas (com @type: Achievement). Isso ajuda o Google a entender que o site é de uma pessoa real e que as conquistas são eventos importantes.

Acessibilidade

Acessibilidade foi um tópico que eu não conhecia bem. Aprendi que:

  • Skip links — permitem que usuários de leitores de tela pulem a navegação;
  • ARIA labels — descrevem elementos interativos para leitores de tela;
  • Contraste de cores — garante que o texto seja legível;
  • Focus visible — indica qual elemento está focado;
  • Teclado — todo o site deve ser navegável com Tab, Enter, Escape, etc.

Uma das correções que fiz foi adicionar aria-expanded ao botão do menu mobile: 

<button class="nav__toggle" id="nav-toggle" aria-expanded="false" aria-controls="nav-menu" aria-label="Abrir menu">

Isso informa ao leitor de tela se o menu está aberto ou fechado.

Dificuldades

O maior desafio foi o contraste de cores. No modo claro, alguns textos ficavam difíceis de ler porque usava cores como #94a3b8 (cinza claro) sobre fundo branco. Verifiquei com ferramentas como o Lighthouse do Chrome e ajustei as cores para atender ao WCAG AA.

Outro problema foi o foco visível. Por padrão, muitos navegadores mostram um contorno azul quando um elemento recebe foco, mas isso pode ser removido ou ficar invisível. Implementei: 

:focus-visible {
    outline: 2px solid var(--color-primary);
    outline-offset: 2px;
}

Isso garante que o foco seja visível apenas quando o usuário navega por teclado (não por mouse), usando a pseudo-classe :focus-visible.

🧹 Fase 7: Refinamentos Finais

A última fase foi dedicada a ajustes finos e polimento. Alguns dos itens mais importantes:

Otimização de Imagens

As imagens estavam em JPG/PNG e aumentavam o tempo de carregamento. Converti para WebP, que oferece melhor compressão. O formato WebP é suportado por todos os navegadores modernos.

Além disso, adicionei loading="lazy" em todas as imagens abaixo da dobra, para que só sejam carregadas quando o usuário rolar até elas: 

<img src="..." alt="..." loading="lazy" decoding="async">

Página 404 Personalizada

Em vez de uma página de erro genérica, criei uma experiência amigável com:

  • Número 404 em degradê;
  • Mensagem acolhedora;
  • Botões para voltar à home ou explorar projetos;
  • Links rápidos para as páginas principais.

Barra de Progresso de Rolagem

Adicionei uma barra de progresso no topo da página que indica quanto do conteúdo foi rolado: 

function updateProgress() {
    const scrollTop = window.scrollY;
    const docHeight = document.documentElement.scrollHeight - window.innerHeight;
    const progress = docHeight > 0 ? (scrollTop / docHeight) * 100 : 0;
    progressBar.style.width = progress + '%';
}

Isso foi um toque a mais que trouxe sensação de modernidade.

Transição Suave de Página

Implementei um fade-out ao sair da página e fade-in ao entrar: 

document.addEventListener('click', (e) => {
    const link = e.target.closest('a');
    if (!link) return;
    // ... verifica se é link interno
    e.preventDefault();
    document.body.classList.add('is-leaving');
    setTimeout(() => {
        window.location.href = link.href;
    }, 400);
});

A classe is-leaving define opacity: 0 no body, e o transition faz o fade-out. Ao carregar a nova página, o body começa com opacity: 0 e transita para 1. Isso cria uma experiência mais coesa.

Uma das dificuldades foi garantir que a transição não interferisse no back do navegador. Adicionei um listener para pageshow que remove a classe is-leaving: 

window.addEventListener('pageshow', () => {
    document.body.classList.remove('is-leaving');
    document.documentElement.classList.remove('is-loading');
    document.documentElement.classList.add('is-loaded');
});

⛰️ Dificuldades Enfrentadas

Nenhum projeto está livre de problemas. Aqui estão os desafios mais marcantes que enfrentei e como os resolvi:

1. Menu Mobile que Não Animava

No início, o menu mobile simplesmente aparecia/escondia com display: none. Quando tentei adicionar uma transição, percebi que era impossível animar um elemento que vai de display: none para display: block.

Solução: usei position: fixed com right: -100% e transicionei a propriedade right para 0. Isso permite animações suaves.

2. Flicker do Modo Escuro

Ao carregar a página, o site piscava entre o tema claro e o escuro por causa do JavaScript rodar depois do HTML.

Solução: script inline no <head> que aplica o tema antes do primeiro render.

3. Links quebrados com baseurl

Como o site está hospedado em /portfolio/, os links relativos quebravam. Colocar ../ manualmente era confuso.

Solução: usar o filtro relative_url do Jekyll para gerar URLs corretas automaticamente.

4. Lightbox Fechando ao Clicar na Imagem

O lightbox fechava mesmo quando o usuário clicava na imagem, porque o evento de clique no overlay (fundo) era propagado.

Solução: verificar se o clique foi no próprio overlay antes de fechar. Usei e.target === lightbox no listener.

5. Legenda Dinâmica no Lightbox

Cada imagem tinha uma legenda diferente, e algumas não tinham. Não queria adicionar atributos data-* em todas as imagens.

Solução: buscar a legenda no DOM com base no card pai. Para post-card, pega o título; para figura-card, pega a legenda.

6. Contraste de Cores

No modo claro, alguns textos estavam com contraste insuficiente (cinza claro sobre branco).

Solução: verifiquei com Lighthouse e ajustei as cores para atender ao WCAG AA. Alterei --color-text-muted no tema claro de #64748b para #475569.

7. Efeito Tilt 3D com Desempenho Ruim

O tilt 3D causava lag em dispositivos com menos recursos, porque usava transformações constantes.

Solução: limitar o efeito a cards de projeto (não a todos os elementos) e usar will-change: transform. Também ajustei o divisor para tornar o movimento mais sutil.

8. Transição de Página que Impedia o Botão "Voltar"

A transição de fade-out/suave fazia com que o botão "Voltar" do navegador não funcionasse corretamente.

Solução: adicionar um listener para pageshow que remove a classe is-leaving.

🎓 O Que Aprendi

Este projeto foi uma jornada de aprendizado intensa. Aqui estão os principais conhecimentos que adquiri:

Desenvolvimento Web

  • HTML semântico: a importância de usar tags como <section>, <article>, <nav> e <main> para SEO e acessibilidade.
  • CSS Grid e Flexbox: entender quando usar cada um. Grid para layouts em duas dimensões, Flexbox para uma dimensão.
  • Variáveis CSS: como usar --var para criar temas dinâmicos com facilidade.
  • Responsividade: usar clamp(), min(), max() e media queries para adaptar o layout.
  • JavaScript moderno: arrow functions, destructuring, spread operator, template literals e módulos ES6.
  • APIs do navegador: IntersectionObserver, matchMedia, localStorage, scrollTo, closest.

Jekyll

  • Layouts e Includes: como reaproveitar código com {% include %} e {% layout %}.
  • Front Matter: metadados que controlam o layout da página.
  • Filtros: relative_url, absolute_url, date, where.
  • Dados estruturados: arquivos em _data/ para gerenciar conteúdo de forma centralizada.
  • Permalinks: URLs amigáveis para SEO.

SEO e Acessibilidade

  • JSON-LD: como estruturar dados para que os mecanismos de busca entendam o conteúdo.
  • Open Graph: metadados para compartilhamento em redes sociais.
  • ARIA: atributos para melhorar a experiência de usuários de leitores de tela.
  • Contraste: a importância de verificar com ferramentas como Lighthouse.
  • Focus management: garantir que o foco do teclado seja visível.

Design e UX

  • Hierarquia visual: usar tamanhos, pesos e espaçamento para guiar o usuário.
  • Microinterações: pequenos detalhes que fazem grande diferença na experiência.
  • Consistência: manter cores, espaçamentos e tipografia consistentes em todas as páginas.
  • Animações com propósito: animações devem guiar, não distrair.
