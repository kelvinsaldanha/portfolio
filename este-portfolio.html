Este Portfólio

Diário de bordo de um site pessoal construído do zero — das primeiras linhas de HTML às microinterações finais.

Visão geral do projeto

Este site nasceu de uma necessidade simples, mas cresceu e se tornou um dos projetos mais desafiadores e gratificantes que já desenvolvi. A ideia inicial era ter um espaço profissional para apresentar meus projetos e experiências na área de equipamentos biomédicos. No processo, percebi que construir um site do zero era, por si só, um projeto que merecia ser documentado — e é exatamente isso que esta página faz.

O que começou como um site estático em HTML, CSS e JavaScript puro evoluiu para um site gerado com Jekyll, com tema claro/escuro, animações, lightbox, sistema de “ver mais” e dezenas de detalhes ajustados ao longo de semanas. Cada seção abaixo reflete uma decisão técnica, um problema superado ou uma lição aprendida.

Abaixo está o processo completo — do planejamento à implementação — incluindo as dificuldades, o que aprendi em cada etapa e por que tomei determinadas decisões. Este é um diário de bordo.

Histórico de desenvolvimento

Antes dos detalhes de cada fase, o contexto: eu estava no curso técnico de Equipamentos Biomédicos, com projetos acadêmicos se acumulando (Eye Tracker CK², Monitor Multiparamétrico, Guia de Respiração), e precisei de um lugar para organizar tudo. Foi aí que decidi construir o próprio site.

O desenvolvimento não foi linear. Tive avanços rápidos e semanas de travamento. Precisei aprender tecnologias novas, revisar decisões e, às vezes, refazer o que já estava “pronto”. Isso faz parte do processo — e é o que documentei aqui.

Concepção e planejamento

Definição do objetivo, levantamento de conteúdo (projetos, publicações, conquistas) e primeiro wireframe. A decisão inicial foi não usar framework de UI — HTML, CSS e JavaScript puro, para entender cada linha.

Primeira versão: HTML/CSS/JS

Primeiras páginas (Home, Sobre, Projetos) com CSS Grid, Flexbox e JavaScript no menu mobile. Primeiras animações de fade-in.

Migração para Jekyll

O site cresceu e a repetição de HTML virou problema. Jekyll permitiu separar navbar, footer e layout. Hospedagem no GitHub Pages, com baseurl: /portfolio.

Modo escuro e personalização

Tema com CSS Custom Properties, detecção de prefers-color-scheme e persistência no localStorage. Cores, sombras e bordas nos dois temas.

Animações e microinterações

Fade-in com Intersection Observer, stagger nos cards, tilt 3D nos cards de projeto e parallax suave no hero.

Lightbox e galeria

Lightbox genérico para projetos e publicações, com teclado (setas, Escape) e clique fora para fechar.

SEO e acessibilidade

JSON-LD, Open Graph, robots.txt, sitemap, skip-link, ARIA e contraste. Testes com Lighthouse.

Refinamentos

Compressão de imagens, correções de responsividade, página 404 personalizada e ajustes de tipografia e espaçamento.

Fase 1: o início — HTML e CSS puro

A primeira decisão foi não usar framework (React, Vue) nem construtor (Wix, WordPress). Queria entender cada linha e ter controle do resultado. Como estudante de equipamentos biomédicos, não tinha formação em desenvolvimento web — tudo seria na prática.

O wireframe

Comecei desenhando à mão. O site precisava de:

  • Home — apresentação, redes e currículo;
  • Sobre — história, formação e interesses;
  • Projetos — galeria técnica e acadêmica;
  • Publicações — aulas práticas, artigos e eventos;
  • Conquistas — medalhas e reconhecimentos;
  • Contato — canais de comunicação.

Pensei em one-page, mas o conteúdo era extenso demais. Múltiplas páginas dão mais trabalho e ficam mais organizadas.

Desafios na fase 1

Grid e Flexbox foram os primeiros obstáculos. Estudei a documentação do MDN. No começo o layout era quase só desktop.

O menu mobile começou como um botão que só mostrava/escondia o menu. Faltavam teclado, clique fora e animação.

Cada erro ensinava. Descobri que display: none impede transição. A solução foi position: fixed com right: -100% e transicionar right.

Fase 2: migração para Jekyll

Depois das primeiras páginas, o navbar, o footer e o <head> se repetiam em todo HTML. Mudar um link exigia editar todas as páginas. Isso não escala.

O Jekyll (gerador de site estático em Ruby) resolve: layouts, includes e HTML final gerado na build. O GitHub Pages roda isso nativamente.

Estrutura do Jekyll

/ 
├── _includes/
│   ├── navbar.html
│   └── footer.html
├── _layouts/
│   └── default.html
├── _data/
│   └── conquistas.yml
├── images/
├── *.html
├── _config.yml
└── style.css

A migração foi mecânica: navbar e footer foram para includes; o layout base passou a envolver o conteúdo de cada página.

Dificuldade: links com baseurl

O site vive em https://kelvinsaldanha.github.io/portfolio/. Todo link interno precisa do prefixo /portfolio. Caminho manual quebra fácil.

A solução é o filtro relative_url (não misturar com a tag link):

{% raw %} 
{{ '/sobre/' | relative_url }}
{% endraw %}

Isso gera /portfolio/sobre/. A tag link é outra coisa — aponta para um arquivo fonte, por exemplo sobre.html. Não se escreve link /sobre/ | relative_url.

Dificuldade: YAML front matter

No início eu colocava só layout: default e esquecia title, description e permalink. O título da aba ficava igual em todas as páginas e o SEO sofría.

layout não é tag Liquid. É chave do front matter no topo do arquivo: 

---
layout: default
title: "Sobre | Kelvin Saldanha"
permalink: /sobre/
---

Defaults no _config.yml evitam repetir o que é comum a todas as páginas: 

defaults:
  - scope:
      path: ""
    values:
      layout: "default"
      author: "Kelvin Saldanha"
      lang: "pt-BR"

Atenção: em páginas Jekyll, qualquer {% raw %}{% … %}{% endraw %} ou {% raw %}{{ … }}{% endraw %} é executado na build. Exemplos de código precisam ir dentro de {% raw %}{% raw %} … {% endraw %}{% endraw %}, senão o GitHub Pages recusa o deploy — foi exatamente o que aconteceu com a primeira versão desta página.

Fase 3: modo escuro e personalização

O modo escuro não é só “inverter cores”. É um sistema que respeita a preferência do sistema e lembra a escolha do usuário.

Como funciona

O CSS usa custom properties em :root (tema escuro padrão) e o override em [data-theme="light"]: 

:root {
    --color-background: #0a0e1a;
    --color-surface: #111827;
    --color-text: #f1f5f9;
    --color-text-muted: #94a3b8;
    --color-primary: #3b82f6;
}

[data-theme="light"] {
    --color-background: #ffffff;
    --color-surface: #f8fafc;
    --color-text: #0f172a;
    --color-text-muted: #475569;
}

O JavaScript lê o sistema com matchMedia('(prefers-color-scheme: dark)') e grava a escolha no localStorage: 

function getTheme() {
    const saved = localStorage.getItem('theme');
    if (saved) return saved;
    return prefersDark.matches ? 'dark' : 'light';
}

function applyTheme(theme) {
    document.documentElement.setAttribute('data-theme', theme);
    localStorage.setItem('theme', theme);
    updateDarkModeIcon(theme);
}

Dificuldades

O trabalho chato é garantir que todo elemento use variável, nunca cor solta. Card com #fff fixo some no tema escuro.

O outro problema é o flash (FOUC): se o tema só aplica no final de script.js, a página pinta no tema errado e depois troca. A correção é um script mínimo no <head> do layout, antes do CSS visível: 

<script>
  (function () {
    var saved = localStorage.getItem('theme');
    var prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
    var theme = saved || (prefersDark ? 'dark' : 'light');
    document.documentElement.setAttribute('data-theme', theme);
  })();
</script>

Sem o botão no navbar, o usuário só segue o sistema. A lógica no JS precisa do toggle no HTML (id="darkmode-toggle"); senão o código existe e a interface não entrega a função.

Fase 4: animações e microinterações

Com o site funcional, as animações passaram a guiar o olhar — desde que não atrapalhem quem pede menos movimento.

Fade-in com Intersection Observer

const observer = new IntersectionObserver((entries) => {
    entries.forEach((entry) => {
        if (entry.isIntersecting) {
            entry.target.classList.add('visible');
            observer.unobserve(entry.target);
        }
    });
}, {
    threshold: 0.1,
    rootMargin: '0px 0px -50px 0px'
});

animatedElements.forEach((el) => observer.observe(el));

.fade-in começa com opacidade 0 e translateY(20px); .visible anima até o estado final no CSS.

Stagger

allFadeElements.forEach((el, index) => {
    const isStagger = staggerSelectors.some((selector) => el.matches(selector));
    if (isStagger) {
        el.style.transitionDelay = (index * 0.05) + 's';
    }
});

Tilt 3D nos cards de projeto

card.addEventListener('mousemove', (e) => {
    const rect = card.getBoundingClientRect();
    const x = e.clientX - rect.left;
    const y = e.clientY - rect.top;
    const rotateX = ((y - centerY) / 40) * -1;
    const rotateY = (x - centerX) / 40;
    card.style.transform =
      'perspective(1000px) rotateX(' + rotateX + 'deg) rotateY(' + rotateY + 'deg)';
});

O divisor 40 controla a intensidade. Em mobile o efeito deve desligar (não há cursor). will-change: transform só enquanto anima — permanente em vários cards custa GPU.

Dificuldades

prefers-reduced-motion no CSS zera duration, mas o JS do tilt/parallax continua calculando se não houver guarda. O CSS: 

@media (prefers-reduced-motion: reduce) {
    *, *::before, *::after {
        animation-duration: 0.01ms !important;
        transition-duration: 0.01ms !important;
        scroll-behavior: auto !important;
    }
}

Fase 5: lightbox e galeria de imagens

O lightbox amplia a imagem, mostra contador e legenda, fecha com Escape ou clique no fundo, e navega com as setas.

Como funciona

O script seleciona .post-card__image e imagens de .figura-card. A legenda vem do DOM (título do post ou caption da figura): 

function abrirLightbox(index) {
    indiceAtual = index;
    const img = itens[indiceAtual];
    imagem.src = img.src;
    imagem.alt = img.alt || '';

    const postCard = img.closest('.post-card');
    if (postCard) {
        const titulo = postCard.querySelector('.post-card__title');
        if (titulo) legenda.textContent = titulo.textContent.trim();
    }

    contador.textContent = (indiceAtual + 1) + ' / ' + itens.length;
    lightbox.classList.add('lightbox--ativo');
    document.body.style.overflow = 'hidden';
}

Dificuldades

Imagem sem src válido (arquivo 404) não deve abrir o modal: 

const itens = Array.from(imagens).filter((img) => {
    return img.src && !img.src.includes('undefined');
});

Clique na imagem não pode fechar o overlay: o listener só fecha se e.target === lightbox. Com o modal aberto, overflow: hidden no body trava o scroll de fundo.

Fase 6: SEO e acessibilidade

Depois de funcional, o site precisava ser encontrado e usável com teclado e leitor de tela.

SEO

  • Meta description única por página (front matter);
  • Open Graph e Twitter Card no layout;
  • JSON-LD com Person, WebSite e lista de award (não Achievement — esse tipo não se encaixa nesse bloco);
  • sitemap gerado pelo plugin jekyll-sitemap — um sitemap.xml estático com URLs .html aponta para páginas que não existem quando o permalink é /sobre/;
  • robots.txt apontando para o sitemap real;
  • permalinks sem extensão.

Acessibilidade

  • Skip-link para o conteúdo principal;
  • ARIA no menu (aria-expanded, aria-controls, aria-label);
  • Contraste (WCAG AA) nos dois temas;
  • :focus-visible para foco só no teclado;
  • Esc fecha o menu e o lightbox.
<button
    class="nav__toggle"
    id="nav-toggle"
    aria-expanded="false"
    aria-controls="nav-menu"
    aria-label="Abrir menu">
:focus-visible {
    outline: 2px solid var(--color-primary);
    outline-offset: 2px;
}

No tema claro, --color-text-muted foi de um cinza fraco para #475569, depois do Lighthouse apontar contraste insuficiente.

Fase 7: refinamentos finais

Imagens

PNG enorme na foto de perfil (mais de 1 MB) e capas em JPG pesado atrasam o LCP. O caminho certo: redimensionar, WebP/AVIF, width/height para evitar CLS, loading="lazy" abaixo da dobra e loading="eager" só no hero. 

<img src="..." alt="..." width="800" height="600" loading="lazy" decoding="async">

Página 404

  • Código 404 visível;
  • Mensagem clara;
  • Atalhos para a home e para projetos.

Barra de progresso de rolagem

function updateProgress() {
    const scrollTop = window.scrollY;
    const docHeight = document.documentElement.scrollHeight - window.innerHeight;
    const progress = docHeight > 0 ? (scrollTop / docHeight) * 100 : 0;
    progressBar.style.width = progress + '%';
}

Transição de página

Fade-out no clique interno e fade-in na entrada. O botão Voltar do navegador quebra se não houver pageshow para limpar a classe: 

document.addEventListener('click', (e) => {
    const link = e.target.closest('a');
    if (!link) return;
    e.preventDefault();
    document.body.classList.add('is-leaving');
    setTimeout(() => {
        window.location.href = link.href;
    }, 400);
});

window.addEventListener('pageshow', () => {
    document.body.classList.remove('is-leaving');
    document.documentElement.classList.add('is-loaded');
});

Dificuldades enfrentadas

1. Menu mobile sem animação

display: none não anima. Solução: position: fixed + right: -100% → 0.

2. Flash do tema

JS no final do body aplica o tema tarde. Solução: script inline no <head>.

3. Links quebrados com baseurl

Solução: {% raw %}{{ '/pagina/' | relative_url }}{% endraw %} em todo link interno.

4. Lightbox fechando ao clicar na imagem

Solução: fechar só se e.target === lightbox.

5. Legenda dinâmica

Solução: ler o card pai (.post-card ou .figura-card), sem data-* em cada imagem.

6. Contraste no tema claro

Solução: Lighthouse + --color-text-muted: #475569.

7. Tilt 3D pesado

Solução: só em .projeto-card, movimento curto, sem will-change permanente, desligado no touch e em reduced-motion.

8. Transição vs. botão Voltar

Solução: listener pageshow removendo is-leaving.

9. Build do GitHub Pages recusando esta página

Documentar Liquid com {% raw %}{% include %}{% endraw %} e {% raw %}{% layout %}{% endraw %} soltos faz o Jekyll tentar executar as tags. include sem arquivo quebra a build; layout nem é tag. Solução: {% raw %}{% raw %} … {% endraw %}{% endraw %} em todo exemplo, e nunca usar layout como tag.

O que aprendi

Desenvolvimento web

  • HTML semântico — section, article, nav, main;
  • Grid e Flexbox — Grid em duas dimensões, Flexbox em uma;
  • Custom properties — temas sem duplicar CSS;
  • Responsividade — clamp(), min(), max(), media queries;
  • JavaScript moderno — arrow functions, const/let, template strings, closest;
  • APIs do navegador — Intersection Observer, matchMedia, localStorage.

Jekyll

  • Layouts e includes — reaproveitar navbar/footer com include de arquivo (navbar.html) e definir o template no front matter (layout: default), não com uma tag layout;
  • Front matter — title, description, permalink por página;
  • Filtros — relative_url, absolute_url, date;
  • _data/ — conteúdo centralizado (ex.: medalhas em YAML);
  • Permalinks — URLs sem .html;
  • Liquid vs. texto — exemplo de tag precisa de raw, senão a build do Pages cai.

SEO e acessibilidade

  • JSON-LD com tipos que existem de fato no schema.org;
  • Open Graph com imagem 1200×630, não a foto de perfil crua;
  • ARIA só onde o HTML semântico não basta;
  • Contraste medido, não “achado”;
  • Foco visível no teclado.

Design e UX

  • Hierarquia visual (tamanho, peso, espaço);
  • Microinteração com propósito;
  • Consistência de token (cor, raio, tipografia);
  • Animação guia — não compete com o conteúdo.
